Native modules are useful, but they raise the maintenance level of a React Native app. I add them only when the product value is worth the native surface area.

![React Native native module illustration connecting JavaScript and Android layers](/assets/blog/react-native-native-modules-when-needed.svg "React Native native module illustration connecting JavaScript and Android layers")

## Define The Responsibility

The decision starts with the feature: does an existing stable package solve it, does the app need a custom Android SDK, or can the requirement be simplified?

## A Maintainable Shape

When native code is needed, I keep the JavaScript API small and documented. The screen should not need to know native setup details.

```bash
cd android
./gradlew clean
./gradlew assembleRelease
./gradlew bundleRelease
```

## Common Architecture Mistakes

- Adding a native dependency before checking release build support.
- Ignoring Android version compatibility.
- Leaving setup steps undocumented for the next developer.
- Wrapping too much behavior in a native module instead of exposing a small capability.

## Production Considerations

Every native dependency belongs in the release checklist. I test clean installs, release builds, and app updates after adding native code.

Native modules are not scary when they are intentional. They just need stronger ownership than a normal JavaScript helper.
