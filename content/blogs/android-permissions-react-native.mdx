Permission handling is UX, not only native configuration. A user should understand why the app asks and what still works if they say no.

![Android permission handling illustration with mobile permission dialog and settings path](/assets/blog/android-permissions-react-native.svg "Android permission handling illustration with mobile permission dialog and settings path")

## The Checklist

I ask for permission near the moment of value. Requesting location on the first screen rarely feels as reasonable as requesting it when the user starts delivery tracking.

## A Practical Pattern

The UI needs states for granted, denied, blocked, unavailable, and not requested. A blocked permission should explain how to open settings instead of looping the same prompt.

```js
const status = await request(PERMISSIONS.ANDROID.POST_NOTIFICATIONS);

if (status === RESULTS.GRANTED) {
  await registerDeviceForPush();
} else {
  setPermissionMessage("Notifications are optional, but order updates may be delayed.");
}
```

## Common Mistakes

- Requesting permissions before explaining the feature.
- Treating denial as a crash path.
- Assuming Android versions behave the same.
- Forgetting to test release builds where permissions and manifests matter.

## Before Shipping

I test permissions on a clean install, after denial, after selecting do not ask again, and after changing the setting manually.
