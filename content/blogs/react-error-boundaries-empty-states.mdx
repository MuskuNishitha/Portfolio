A resilient React app does not pretend failures never happen. It gives users a clear path when a section is empty, unavailable, or blocked by an error.

![React fallback UI illustration with error and empty state panels](/assets/blog/react-error-boundaries-empty-states.svg "React fallback UI illustration with error and empty state panels")

## The Checklist

I treat empty states and error states separately. Empty means the request worked but there is nothing to show. Error means something prevented the app from getting or rendering the data.

## A Practical Pattern

For feature-level errors, a local fallback is usually better than blanking the full app. A dashboard chart can fail while the rest of the page remains useful.

```jsx
function EmptyState({ title, message, action }) {
  return (
    <section role="status" className="rounded-lg border p-6 text-center">
      <h2>{title}</h2>
      <p>{message}</p>
      {action}
    </section>
  );
}
```

## Common Mistakes

- Using a generic something went wrong message for every failure.
- Hiding the retry button inside a toast that disappears.
- Treating zero results as an error.
- Letting one broken optional widget crash the whole route.

## Before Shipping

Error boundaries should log enough context to find the failing feature, but the user-facing message should stay short and calm.
