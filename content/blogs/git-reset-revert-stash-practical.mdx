Reset, revert, and stash solve different problems. Confusing them can lose work or make shared history harder to understand.

![Git history tool illustration with reset revert and stash paths](/assets/blog/git-reset-revert-stash-practical.svg "Git history tool illustration with reset revert and stash paths")

## Where The Problem Starts

I use stash for temporary local changes, revert for undoing a commit that may already be shared, and reset mostly for local history cleanup before pushing.

## The Pattern I Use

The safest question is: has this commit been shared? If yes, revert is usually safer. If no, reset may be acceptable when used deliberately.

```bash
git stash push -m "wip contact form"
git revert abc1234
git reset --soft HEAD~1
```

## Common Mistakes

- Using hard reset to clean up without checking uncommitted work.
- Rewriting shared history without coordinating.
- Stashing changes and forgetting they exist.
- Using revert for a local commit that could simply be amended.

## Production Notes

On production branches, I prefer reversible history. A revert commit explains what happened and keeps the timeline honest.
