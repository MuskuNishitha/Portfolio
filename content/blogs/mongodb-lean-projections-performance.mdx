## Core Concepts

The core model for this article is the Mongoose lean and projection performance pattern. I use these ideas as a review checklist before reaching for a library, refactor, or deployment change.

## Practical Code Examples

### Use lean reads and projections for list endpoints

This first example keeps the article grounded in Mongoose lean and projection performance pattern. It is intentionally small enough to paste into a project and adapt, but it shows the boundary that matters: using lean reads, selecting only rendered fields, avoiding hydration cost, and keeping API payloads small.

```js
const projects = await Project.find({ isPublished: true })
  .select("title slug summary imageUrl techStack createdAt")
  .sort({ createdAt: -1 })
  .limit(12)
  .lean();

```

## Common Mistakes

Most problems around Using lean And Projections For MongoDB Performance are not caused by a lack of effort. They come from solving one visible issue while leaving the surrounding contract unclear.

- Fixing only the screen where slow list pages, huge response bodies, accidental private fields, and CPU time spent hydrating documents that are never saved appeared, while another route still uses the old pattern.
- Skipping the direct production-style check because the local development flow looked fine.
- Adding indexes to every field without checking whether they support a real query.
- Returning private or admin-only fields because the API did not use projection.
- Embedding large changing arrays that make small updates rewrite too much data.
- Assuming Mongoose validators run the same way for saves and update operations.
- Computing dashboard totals in the browser after sending thousands of documents over the network.
