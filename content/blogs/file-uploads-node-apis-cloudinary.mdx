File uploads should be designed as a flow, not a single endpoint. The API receives a file, validates it, stores it, saves references, and cleans up failures.

![Node.js file upload illustration with image storage and database reference](/assets/blog/file-uploads-node-apis-cloudinary.svg "Node.js file upload illustration with image storage and database reference")

## Define The Responsibility

Cloudinary is a common storage option for images, but the architecture matters even if the storage provider changes. The database should store the public URL and provider id, not the raw file.

## A Maintainable Shape

I validate file type and size before upload. After storage succeeds, the product document can save the image URL and public id so replacements and deletes remain possible.

```js
const uploadResult = await cloudinary.uploader.upload(file.path, {
  folder: "products",
  resource_type: "image",
});

await Product.findByIdAndUpdate(productId, {
  imageUrl: uploadResult.secure_url,
  imagePublicId: uploadResult.public_id,
});
```

## Common Architecture Mistakes

- Accepting any file type because the frontend has a file picker.
- Saving only the image URL and losing the provider id needed for cleanup.
- Leaving temporary files after failed uploads.
- Uploading large originals when the UI only needs a compressed display image.

## Production Considerations

Uploads need limits, error messages, and monitoring because storage costs and payload size can grow quietly.
