A pull request should make review easier, not just move code from one branch to another. The reviewer needs context, risk, and proof that the change was tested.

![GitHub pull request review illustration with checklist and changed files](/assets/blog/pull-request-review-checklist-github.svg "GitHub pull request review illustration with checklist and changed files")

## The Checklist

I look for scope first. If a PR changes blog content, API routes, theme behavior, and deployment config together, it becomes harder to review safely.

## A Practical Pattern

A good PR description includes what changed, why it changed, how it was tested, screenshots for UI work, and notes about migrations or environment variables.

```bash
git fetch origin
git switch feature/blog-filters
git rebase origin/main
git push --force-with-lease
```

## Common Mistakes

- Opening a large PR without explaining the goal.
- Skipping screenshots for visual changes.
- Changing API response shapes without updating frontend callers.
- Treating review comments as blockers instead of collaboration.

## Before Shipping

For deployment-sensitive PRs, I also ask how to roll back. A simple answer can save a lot of stress later.
